# Тропа — AI Hiking Planner

Сервис подбирает однодневные пешие маршруты вокруг Гренобля по запросу обычным языком. Пример: «Найди поход рядом с Греноблем на 4 часа, с озером, не слишком сложный». Локальная языковая модель разбирает условия, сервис получает проверенные маршруты и прогноз через MCP, затем модель ранжирует варианты. Сайт объясняет выбор на основе проверенных характеристик маршрутов.

**Работающий сайт:** [http://2.31.65.158](http://2.31.65.158)

**Интерактивная HTML-презентация:** [http://2.31.65.158/presentation](http://2.31.65.158/presentation)

> MVP ограничен окрестностями Гренобля. Длительность, набор высоты и сложность взяты из исходных карточек маршрутов. Прогноз относится к точке старта и не гарантирует безопасность всей тропы.

## Пользователь и сценарий

Пользователь планирует прогулку и знает, сколько времени готов идти, какой уровень сложности ему подходит и что хочет увидеть. Он вводит пожелания на сайте и получает до трёх вариантов с длительностью, длиной, набором высоты, прогнозом, объяснением и ссылкой на исходное описание. Если совпадений нет, сервис явно называет отличия ближайших вариантов.

## Границы MVP

- 20 маршрутов вокруг Гренобля с характеристиками и ссылками на конкретные карточки [Grenoble Alpes Tourisme](https://www.grenoble-tourisme.com/fr/faire/toute-offre-outdoor/marcher-courir/). Это вручную отобранный каталог, а не живой поиск по всему сайту.
- Запросы на русском; поддерживаются верхняя и нижняя границы длительности, желаемый набор высоты, сложность, озеро и явно названные признаки (лес, панорама, водопад, луга, история). «Больше 2 часов» означает строго более 2 часов, а «высота 400 м» трактуется как **набор высоты**.
- Прогноз [Open-Meteo](https://open-meteo.com/en/docs) для даты в пределах 16 дней. Погода отображается для координат старта маршрута.
- Для трёх маршрутов через Лютель показано [реальное фото озера Лютель](https://commons.wikimedia.org/wiki/File:RN_lac_Luitel_abc6.jpg) с указанием автора Patafisik и лицензии [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). Остальные карточки используют декоративную иллюстрацию Альп и прямо помечены как иллюстрации. Ссылки на местоположение открывают OpenStreetMap.
- Не проверяются состояние троп, наличие льда и снега по всему маршруту, транспорт и бронирование.

Подробные условия и критерии приёмки: [SPEC.md](SPEC.md).

## Архитектура

![Схема архитектуры: запрос через сайт и FastAPI попадает в первую LLM, затем MCP-клиент обращается к MCP-серверу маршрутов и погоды, после чего вторая LLM формирует ответ](docs/architecture.png)

1. **Web → FastAPI.** Валидация запроса и даты.
2. **LLM №1.** Ollama `qwen3:4b-instruct` извлекает параметры запроса в JSON по схеме Pydantic.
3. **MCP-клиент → MCP-сервер.** Отдельный Python-процесс обменивается сообщениями по `stdio`. Backend вызывает `search_routes` и `get_weather`; сервер читает каталог `data/routes.json` и получает прогноз Open-Meteo. Также доступен `get_route_details`.
4. **Баллы и LLM №2.** Код считает прозрачный балл соответствия 0–100; модель получает кандидатов, прогноз и баллы, выбирает до трёх маршрутов. Итоговый порядок определяется баллом.
5. **Проверка и вывод.** Backend принимает только известные ID маршрутов. Название, цифры, ссылки и краткое объяснение формируются из каталога, а не из свободного текста модели. В интерфейсе можно открыть журнал этапов LLM → MCP → Ranking → LLM.

В рамках одного запроса MCP реально используется для доступа к данным; это не декоративное упоминание протокола. Сервер определён в `app/mcp_server.py`, вызовы клиента — в `app/planner.py`.

### Ранжирование

Баллы в `app/ranking.py` складываются из близости длительности и набора высоты к запросу (вместе до 35), допустимой сложности (25), наличия озера при запросе (20), запрошенных признаков (10), прогноза у старта (10). Если указан только набор высоты, все 35 баллов соответствия времени переходят ему; если указаны оба параметра, распределение 20/15. Если прогноз недоступен, погодная часть получает нейтральные 5 баллов. Это **оценка соответствия запросу**, не вероятность безопасности. MCP сначала отсеивает нарушения жёстких ограничений; набор высоты учитывается как пожелание, а не жёсткий предел.

Офлайн-оценка порядка — **NDCG@3 = 0,853** на шести вручную размеченных наборах кандидатов (релевантность 0–3). Данные, скрипт и покейсные результаты: `eval/ranking_cases.json`, `eval/ranking_eval.py`, `eval/ranking_results.json`. Метрика проверяет только формулу ранжирования с нейтральной погодой, отдельно от качества извлечения запроса LLM и живого прогноза. Небольшая разметка не доказывает качество на всех запросах.

## Стек

Python 3.11+, FastAPI, официальный Python MCP SDK, Ollama с Qwen3 4B Instruct, Open-Meteo, HTML/CSS/JS. На сервере используются Nginx и systemd. Внешний LLM API-ключ не нужен.

## Запуск локально

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
ollama pull qwen3:4b-instruct
ollama serve
```

В другом терминале:

```bash
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте `http://127.0.0.1:8000`. Для другого адреса Ollama задайте `OLLAMA_URL`; для другой установленной модели — `OLLAMA_MODEL`. Модель должна поддерживать структурированный JSON-ответ. `GET /api/health` проверяет доступность модели. Запрос может занимать несколько минут на CPU.

## Развёртывание на Ubuntu

Проект развёрнут на Ubuntu 26.04, 4 vCPU, 8 ГБ RAM. Ollama установлен как systemd-сервис и слушает только `127.0.0.1:11434`. Сайт запускается отдельным пользователем `hiking` на `127.0.0.1:8000`; Nginx публикует его на порту 80. Файлы конфигурации находятся в `deploy/`.

Для повторного развёртывания на чистой Ubuntu установите Ollama [по официальной инструкции](https://docs.ollama.com/linux), загрузите модель, установите `python3-venv` и `nginx`, скопируйте репозиторий в `/opt/ai-hiking`, затем выполните от root:

```bash
cd /opt/ai-hiking
ollama pull qwen3:4b-instruct
bash deploy/install.sh
systemctl status ai-hiking
curl http://127.0.0.1/api/health
```

Для публичной ссылки по IP используется HTTP. Домен и HTTPS — следующий шаг для постоянной эксплуатации; секретов или личных данных пользователей сервис не хранит.

### Автоматическое развёртывание

`.github/workflows/deploy.yml` проверяет каталог, Python и NDCG на PR. После **merge в `main`** событие `push` запускает те же проверки, отправляет архив релиза на VPS по SSH и проверяет публичный `/api/health`. Работает также при прямом push в `main`.

На сервере отдельный пользователь `deploy` имеет ограниченный ключ: принудительная SSH-команда принимает архив, обновляет `/opt/ai-hiking`, устанавливает зависимости в виртуальное окружение пользователя `hiking` и перезапускает systemd-сервис. Настройка сервера: `deploy/setup-cd.sh` и `deploy/receive-release.sh`. Приватный ключ хранится только в GitHub Actions secret `DEPLOY_SSH_KEY`; закреплённый ключ сервера — в `DEPLOY_KNOWN_HOSTS`. Они не находятся в репозитории. Если проверки или деплой не проходят, workflow помечает запуск как failed.

## Eval и разбор ошибок

Проверка включает основной запрос, короткий лёгкий маршрут, отсутствие точного совпадения, сезонность, дату вне горизонта прогноза и фактические MCP-вызовы. Фиксируем время ответа, выбранные ID, соответствие ограничению длительности и сложности, наличие ссылок и обработку недоступного прогноза. Набор сценариев и проверочный скрипт находятся в `eval/`.

**Прогон исправленной ветки 26 октября 2026: 6/6 сквозных сценариев прошли** на каталоге из 20 маршрутов, включая дословные запросы о наборе высоты 400 м и длительности больше 2 часов. Дополнительно NDCG@3 = 0,853. Подробности — в [eval/RESULTS.md](eval/RESULTS.md); машинные результаты — в `eval/`.
