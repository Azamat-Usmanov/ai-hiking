# Eval: фактический прогон

Дата проверки: **26 октября 2026**. Среда: обновлённая ветка на отдельном внутреннем порту того же VPS (`127.0.0.1:8001`), Ubuntu 26.04, 4 vCPU, 8 ГБ RAM, Ollama `qwen3:4b-instruct`. Скрипт: `eval/run_eval.py`. Проверки выполнены через HTTP, включая оба вызова LLM и MCP. Публичный сервис при этом не менялся.

**Итог:** 7/7 контрольных сквозных сценариев прошли с каталогом из 20 маршрутов. Скрипт проверял существование ID в каталоге, неизменность расстояния, длительности, набора высоты, сложности и исходной ссылки, соблюдение жёстких ограничений при точном совпадении и наличие обоих MCP-вызовов в журнале. Отдельно проверяются разбор 400 м, строгая нижняя граница времени, восемь кандидатов и максимум шесть карточек. Время зависит от прогрева модели, погоды и нагрузки на CPU; широкий запрос занял 37,4 с.

## Качество ранжирования

Офлайн-метрика **NDCG@3 = 0,853** на шести вручную размеченных запросах: релевантность кандидата от 0 (не подходит) до 3 (лучший вариант). Проверяется формула баллов без LLM и с нейтральной погодой; каждый набор содержит пять заранее выбранных кандидатов. Данные и воспроизводимый расчёт: `eval/ranking_cases.json`, `eval/ranking_eval.py`, `eval/ranking_results.json`. Команда: `python -m eval.ranking_eval` из корня проекта.

Два показательных промаха: для лёгкой двухчасовой прогулки по лесу формула ставит перед лучшим вариантом более длинный бельведер Визиля (NDCG@3 0,650); запрос «без технических участков» пока не извлекается в структурированные ограничения, поэтому опасный для такого условия маршрут может оказаться первым (NDCG@3 0,470 в пятом наборе). Следующее улучшение — распознавать отрицательные ограничения и лучше учитывать степень соответствия признакам.

Дополнительная проверка MCP напрямую: для даты 20 ноября маршрут `quirlies` возвращается с причиной «вне опубликованного периода маршрута», а не как точное совпадение.

## Обнаруженные ошибки и исправления

1. **Первый вариант схемы разбора допускал необязательные поля.** Модель возвращала только `max_hours`, пропускала озеро и сложность. Сделали все три поля обязательными в JSON-схеме и отдельно проверили фактический разбор: `4`, `moderate`, `true`.
2. **Локальная модель зациклилась на генерации даты в JSON.** Дату перенесли в отдельное поле интерфейса; модель больше не генерирует её. При неверной дате применяется текущая дата.
3. **Свободное объяснение модели ошибочно назвало маршрут на 3 ч 45 мин превышающим лимит 4 ч.** Модель теперь выбирает и ранжирует только ID из списка допустимых кандидатов. Фактические характеристики и краткое объяснение выводит код из исходного каталога.
4. **На запрос о высоте модель повторяла значения в массиве `features` до обрыва JSON.** Убрали массив из схемы LLM, ограниченные признаки извлекаются кодом; при повторном невалидном JSON используется явный резервный разбор. Набор высоты получает собственное поле и влияет на поиск и балл.
5. **«30 минут» модель один раз интерпретировала как 30 часов.** Числовые минуты и часы нормализуются из исходного запроса до валидации ответа модели.
6. **«Больше 2 часов» возвращало маршруты ровно по 2 часа.** Код ошибочно записывал любое число часов как верхнюю границу. Теперь нижняя и верхняя границы разделены; MCP проверяет строгий оператор `>` для «больше».

## Оставшиеся ограничения

- Набор состоит из 20 вручную отобранных маршрутов одного региона; отсутствие результата не означает, что в местности нет других троп.
- 7/7 сценариев проверяют основные ветки, но не доказывают качество на произвольных формулировках. Особенно нужно расширять запросы с синонимами и несколькими условиями.
- Прогноз относится к точке старта. Состояние высокогорной тропы, снег, закрытия и опасные участки требуют отдельной проверки перед походом.
- При недоступной внешней погоде MCP возвращает статус `unavailable`; этот отказ предусмотрен в коде, но отдельный принудительный сбой API в данном прогоне не создавался.
